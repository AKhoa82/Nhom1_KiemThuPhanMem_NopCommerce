# SCRUM-96 B01 — code and UI review, 24/11/2026

**Historical verdict before the follow-up fixes: changes requested.** The cart conservation path passed the local 8/8 UI run and 6/6 service tests, but the buyer-facing recovery flow was not ready for acceptance. This is an independent technical review; it does not replace the group lead's required sign-off. The current assessment is in the follow-up section below.

## Findings

1. **High — multi-store recovery message points to an empty cart.** `CustomerRegistrationService.SignInCustomerAsync` still redirects to the current store's cart on a migration warning. The `MERGE-MULTISTORE` UI/SQL evidence shows the rejected Red/S item remained in guest store 1 while login was attempted in store 2, whose cart was empty after the accepted Blue/M line moved. The localized warning now says the item remains in the guest cart, but neither names store 1 nor provides a path to its cart. This fails the plan's requirement that the buyer can see and act on the remaining item. Evidence: `RUN-20261124-B01-WARNING-MULTISTORE/multistore-store2-rejected-login.png`, `multistore-store1-after-rejection.sql.txt`, and `multistore-store2-after-rejection.sql.txt`. Fix the message/route so every rejected item identifies its store and the buyer can reach it; add a UI assertion for that recovery path.

2. **Medium — rejection handling is bypassed by some sign-in callers.** `SignInCustomerAsync` now returns a cart redirect on migration failure, but `CustomerController` ignores that result after password recovery (`:969`), account activation (`:1448`), email revalidation (`:1767`), and password change (`:2008`). Account activation and password recovery can begin from a guest session with a cart, so those actions can continue to their normal view even though sign-in was rejected. The standard login and registration paths return the result correctly. Propagate the migration outcome through the callers that can run from a guest session, then test at least activation or recovery with a rejected cart item.

3. **Medium — a rejected line can clear the account's checkout selections.** Migration calls `AddToCartAsync` for each source line (`ShoppingCartService.cs:1893`). `AddToCartAsync` calls `ResetCheckoutDataAsync(customer, storeId)` before validating stock (`:1616`); that reset clears reward-points choice, shipping/pickup choice, and selected payment method by default (`:1945-1980`). On a failed merge, the buyer remains signed out and the account cart quantity is unchanged, yet those account selections have already been cleared. Add a regression test for rejected migration with preselected checkout data and move the reset until an item is actually accepted, or document and approve the intended side effect.
